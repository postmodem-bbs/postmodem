# M2 — Usable board

Status: **M2a done, released as [0.1.0](../releases/0.1.0.md)** (2026-11-19); M2b next · planned 2026-11-18 · builds on [M1](M1.md) and
[ADR 0019](../adr/0019-package-tiers-and-essentials-profile.md) (package tiers)

## Goal

At the end of **M2a** the board can go on a public machine as a staging environment: people
register, post, reply, send private messages, search and report posts; moderators moderate;
the admin runs the board from the browser; nothing is lost if something breaks. **M2b** then
completes the platform services and extension points that the tier A packages need (M3),
shaped by the first packages and by what staging testers report.

The first tier A packages (`quick-reply`, `reports`, `unread-tracking`) are built in M2a,
together with the extension points they use. Each extension point lands with a real user,
not ahead of one (ADR 0019).

### Demo that defines "M2a done"

1. A staging board (stack mode behind Caddy, real SMTP) runs the `essentials` profile with
   the demo content.
2. An invited visitor registers (proof-of-work check, e-mail confirmation), posts a topic, replies with quick
   reply, edits and deletes their own post, quotes someone, sends a private message, and gets
   an e-mail when a watched topic gets a reply.
3. Unread topics and forums are marked exactly, per topic, and "mark all read" works.
4. A member reports a post; a moderator sees the report count, opens the queue, locks, moves,
   splits or deletes, and every action is in the audit log with its reason.
5. The admin edits forums, groups and permissions in the browser and checks a permission
   with the simulator; `postmodem backup` and `restore` round-trip the whole board.
6. A member exports their data and deletes their account.
7. All new pages pass e2e + axe (light, dark, forced-dark), work without JavaScript, and the
   performance budget holds under a load test that mixes reading with posting.

## Slices — M2a, public beta (~13–17 days)

### Slice 1 — Posting (~2–3 d) *(done 2026-11-18)*

> Rules in `@postmodem/core` (`posting.ts`): `createTopic`, `reply`, `editPost`, `deletePost`,
> and `may.*` predicates that the pages use for their buttons, so both follow one set of rules.
> phpBB2 behaviour kept: members delete their own post only while it is the last one (the only
> post takes its topic along), an edit counts once someone has replied, locked topics and
> forums take nothing from members, moderators skip the flood interval
> (`core.posting.floodSeconds`, default 15) and a volume throttle (30 posts an hour, then
> growing waits). Counters update incrementally; deletes recount. UI on phpBB2's
> `posting.php?mode=newtopic|reply|quote|editpost|delete`: plain forms, preview, a BBCode
> toolbar when JavaScript runs; quoting drops `[hide]` blocks so it can't reveal them. Guest
> posting waits for slice 7 (CAPTCHA). E2E covers it with and without JavaScript in Chromium
> and Firefox (the e2e board runs with no flood interval).

- New topic, reply, quote, edit and delete own posts with the core capabilities
  (`topic.create`, `topic.reply`, `post.edit.own`, `post.delete.own`); plain forms first,
  enhanced with a BBCode toolbar and live preview when JavaScript is on.
- Counters (topic, forum, user post counts, last post) updated incrementally in the same
  transaction; posts rendered on write.
- Posting and PM rate limits through the existing throttle service; flood interval setting.
- Locked topics and forums refuse replies, except for moderators.

### Slice 2 — Moderation (~2 d) *(done 2026-11-18)*

> `@postmodem/core` `moderation.ts`: lock, topic type, move (optional "moved" shadow), split,
> merge (the source becomes a shadow, so its links lead to the merged topic) and delete (posts
> leave their authors' counts), each checked per forum and audited with the moderator's reason.
> UI on phpBB2's `modcp.php?t=ID`. Bans by user, IP and e-mail with `*` wildcards and optional
> expiry, in one list checked at sign-in, registration and on every request (cached 15 s, so
> every replica applies a new ban within that). A banned IP gets only a "banned" page; a banned
> member is signed out. `postmodem ban list|user|ip|email|remove` until the admin panel.

- Vanilla phpBB2 modcp: lock/unlock, move (with an optional shadow topic), split, merge,
  delete (visibility `core:deleted`, restorable by admins), sticky/announcement.
- Bans by user, IP and e-mail (vanilla core); banned users keep reading if the board allows.
- Every action is a **moderation event** with actor and reason (extension point #9) and goes
  into the audit log.

### Slice 3 — Package runtime v0 (~2–3 d) *(done 2026-11-18)*

> `@postmodem/core` `packages.ts` defines a package: capabilities with default grants for the
> built-in roles (#7), settings, migrations (own table `pm_package_migrations`, run for every
> installed package), and at setup events (#9 and the content lifecycle), listing decorations
> (#2) and slots. Slots are data the core renders (links with counts, forms), so a package
> can't break a page's accessibility or CSP. First-party packages live in `@postmodem/modules`
> (dependency-cruiser keeps them on the package API); their own pages (e.g. `report.php`) are
> routes in the app that 404 when the package is off. Enabled set: `core.packages.enabled`, or
> the `POSTMODEM_PROFILE` list (`vanilla`, `essentials` by default, `przemo`), read per call so
> `postmodem packages enable|disable` applies to a running board. A failing package is logged
> and loses its contribution, never the page. Package strings live in core.ftl for now.

- Package manifest, loader, enable/disable, per-package migrations and settings schema;
  `vanilla` and `essentials` profiles; `postmodem packages list|enable|disable`.
- Extension points used by slice 4: **registries** (#7: capabilities, topic types,
  providers), **listing modifiers** (#2), **moderation events** (#9), and render **slots**.
- Packages live in the repository (`packages/pkg-*`), built and tested with the core.

### Slice 4 — First tier A packages (~3 d) *(done 2026-11-18)*

> `quick-reply` (a reply form under the posts), `reports` (Przemo's `report.php`: report with a
> reason, one open report per member and post, a header link with the open count for
> moderators of that forum, a queue to close reports with an outcome, audited) and
> `unread-tracking` (per-member marks per topic, forum and board; a 30-day horizon,
> `unread.days`; "new" badges on topics and forums from one grouped query; "mark forum / all
> read"). Not yet: importing Przemo's `report_*` and `read_history` (importer slices, moved to [Beta](Beta.md) by [ADR 0024](../adr/0024-importer-work-in-the-beta-phase.md)), and
> a reporter notification (slice 5). The core's own "new since last visit" isn't built: the
> package does it better and is on by default.
> Posting limit is now a setting, `core.posting.perHour` (default 30, 0 = off).

- `quick-reply` (T1): a slot on the topic page posting to the core reply endpoint.
- `reports` (T2): report a post with a reason; moderator queue with a count badge (no
  realtime yet); close with an outcome; notifies the reporter. The importer slice for Przemo's
  `report_*` data moved to [Beta](Beta.md).
- `unread-tracking` (T2): core gets vanilla "new since last visit" first; the package adds
  exact per-user, per-topic watermarks (batched writes like the view counter), "mark forum /
  all read", and imports `read_history`.

### Slice 5 — Private messages and notifications (~2 d) *(done 2026-11-19)*

> Core `messaging.ts` (`pm.send` capability, inbox limit `core.pm.inboxLimit`, each side
> deletes its own view) on phpBB2's `privmsg.php` (inbox, sent, read, write, reply with a
> quote); the posting limit counts messages. Topic watching (`topics_watch`): one e-mail per
> topic until the watcher visits again, only to watchers who can still read it; members watch
> their own topics and replies unless they turn it off. E-mail on a new message (never its
> text). Closing a report sends the reporter a message with the outcome. The importer brings
> phpBB2's private messages (by `privmsgs_type`, so each side sees exactly what it saw),
> watches and both notification preferences.
> Added because a staging board needs them: `/account` (profile, signature, notification
> choices, password change, which signs out other devices) and signatures under posts. Also
> fixed: `[you]` showed "Guest" to signed-in readers.

M2b follows up with [self-service e-mail changes (#42)](https://github.com/postmodem-bbs/postmodem/issues/42).
Members confirm a link sent to the new address before the board switches to it.

- PM inbox, sent, outbox; reply and quote; per-user limits; e-mail notice of a new PM.
- Topic watching (vanilla `topics_watch`, imported) with one e-mail per topic until the
  watcher visits again; all mail through the job queue.

### Slice 6 — Search and memberlist (~1–2 d) *(done 2026-11-19)*

> A search provider port (#7) on the database: SQLite FTS5 (contentless) and Postgres
> `tsvector` with a GIN index, text folded like slugs on both sides (so "lodz" finds "Łódź"),
> every word required, prefixes match. Only plain text is indexed (no quotes, no `[hide]`);
> results are filtered by visibility and the reader's forums at query time, newest first, and
> stop at 1000 like phpBB2. Indexed on write, re-indexed after moderation moves posts,
> rebuilt by `postmodem search rebuild` and after imports (219k posts in 16 s). phpBB2's
> `search.php` parameters; `core.search.perMinute` limits searches per IP. On one core, a word
> in 50,000 of 219,000 posts answers in about 100 ms. `memberlist.php` with phpBB2's sort
> modes; `core.memberlist.guests` hides it from guests.

- Database full-text search behind a search provider (#7): SQLite FTS5, Postgres
  `tsvector`; permission-filtered results; filters by author, forum and date.
- Memberlist with sorting; hidden for guests if the board says so.

### Slice 7 — Anti-abuse and invites (~1–2 d) *(done 2026-11-19)*

> A self-hosted proof of work on registration (`lib/server/captcha.ts`): an HMAC-signed,
> expiring SHA-256 challenge the browser solves in the background (~25,000 hashes on average),
> each accepted once; without JavaScript the form passes after a 5-second wait. Invite-only
> registration (`core.registration.inviteOnly`): `postmodem invite create|list|revoke`, codes
> shown once and stored hashed, with uses and expiry. New members (`core.newMembers.posts`,
> default 3) can't post links or send private messages yet; moderators and admins are exempt.
> Guest posting stays off: when it arrives, it uses the same check.

- CAPTCHA provider interface with a built-in, self-hosted **proof-of-work** provider
  (invisible, no images, no third-party requests), on registration and on guest posting
  when that is allowed. Without JavaScript the form falls back to a short wait.
- Registration modes: open, **invite-only** (admin-issued single-use or limited invite
  links, with expiry; the beta runs this way), or closed.
- New accounts: limits on links and PMs until a few posts are approved by time or count.

### Slice 8 — Admin panel v0 (~2–3 d) *(done 2026-11-19)*

> `/admin`: overview (with a warning while mail only goes to the log), board settings (a
> curated form over the typed settings), forums (create, edit, move, lock, delete when empty),
> groups and members, permissions (grants editor, never the last board-wide administrator, and
> the simulator), members (find, ban for good or N days, lift, activate, force a password
> reset), IP/e-mail bans and invite links, packages, and the audit log. Each page needs
> `admin.access` and its own capability; every change is audited. The demo Admin has no
> password (staging runs the demo content in public): CI sets one with
> `postmodem user set-password` for the e2e tests.

- Board settings (the typed settings service), forum tree (create, edit, move, delete with
  content handling), groups and memberships, permissions (grants editor plus the simulator,
  i.e. `perms explain` in the browser), users (find, activate, ban, force password reset),
  audit log viewer, packages on/off.

### Slice 9 — Operations, privacy and staging (~2 d) *(done 2026-11-19)*

> `postmodem backup` / `restore` for SQLite (online `VACUUM INTO` plus uploads, manifest,
> restore keeps what it replaces); Postgres boards use the database container's `pg_dump`
> (CONTAINERS.md §4.5). Member data export (`/account/export`, JSON) and account deletion
> (password-confirmed; personal data erased, posts kept as "Deleted user" or removed per
> `core.accounts.deletedPosts`). An editable privacy notice (`/privacy`, linked from every page
> and from registration) with a built-in text that says what is actually stored. The staging
> guide is CONTAINERS.md §4.6. The import report keeps Przemo's feature switches in the
> anonymised bundle. Fixed on the way: the `migrate` role didn't apply package migrations.
> The import summary naming tier C data "not planned" moved to [Beta](Beta.md) ([ADR 0024](../adr/0024-importer-work-in-the-beta-phase.md)).

- `postmodem backup` / `restore`: SQLite online backup or `pg_dump`, plus uploads; restore
  tested in CI.
- Member data export (JSON) and account deletion: personal data and the profile are erased,
  posts stay under "deleted user" (phpBB2 behaviour); removing posts too is a board option.
  Through extension point #13, so packages add and erase their own data.
- A privacy page and board rules page editable by the admin; only essential cookies, so no
  consent banner.
- Staging guide in CONTAINERS.md: stack mode, SMTP, scheduled backups, updates.
- Report bundle gains Przemo's feature switches (ADR 0019); the import summary names tier C
  data as "not planned".

## Slices — M2b, platform v0 (~11–16 days)

### Slice 10 — Platform services v0 (~3–4 d) *(done 2026-11-19)*

> The five services of PLATFORM-SERVICES.md as first-party APIs (`@postmodem/core`
> `platform/`), declared in a package's definition next to its settings. Rules are TypeScript
> until the tier-1 manifest (M4). **Preferences**: members' choices stored with the account,
> guests' in one cookie (`pm_prefs`), the account winning over the device; the colour scheme
> and language are the first two (0.1.0's cookies still read). **Entity fields**: one side
> table per target, a page's fields in one query, read/write rules, personal ones in the
> export. **Collections**: `/x/<package>/c/<name>` as JSON and as plain forms; server-set
> authors, rate limit, hiding, retention in the scheduler's housekeeping. **Channels**:
> `/x/stream` (server-sent events, Last-Event-ID replay for 2 minutes), on Postgres
> LISTEN/NOTIFY in stack mode, Valkey with `POSTMODEM_REALTIME_URL`; first users: new replies
> on an open topic (a link, nothing moves), and the header's message and report counts.
> **Counters**: buffered and flushed every 10 s, in memory or in Valkey shared by every replica
> (`POSTMODEM_COUNTERS_URL`); topic views moved onto them. Migration 0014. The first package
> using fields and collections lands in slice 11.

[Login security (#33)](https://github.com/postmodem-bbs/postmodem/issues/33) adds a configurable
cooldown for each identifier and IP pair, an optional letter-and-number requirement, a
configurable minimum password length, and optional session IP binding. The baseline core
throttles and password checks apply in every profile. `essentials` and `przemo` enable the
package by default. Set `login-security.auth.maxFailures`, `blockMinutes`,
`minPasswordLength`, `requireLettersAndNumbers`, and `bindSessionIp` through board settings
using the `login-security.auth.` prefix for each key.

Przemo imports carry over the board's failure limit, lockout duration in minutes, minimum
password length (with the core floor), and mixed-password setting. The core already rejects
passwords equal to the username. Historical lockouts and per-user legacy IP settings remain
reported. Session IP binding is a fresh board choice.

[Package privacy (#43)](https://github.com/postmodem-bbs/postmodem/issues/43) adds EP #13.
The account export includes reports the member filed, without moderator IDs. Account deletion
erases those reports in the same transaction, even while the package is disabled. Moderation
audit records and reports filed by other members follow the existing retention policy.

### Slice 12 — Finishing (~2–3 d)
Markdown input and mentions; notification preferences and digests; CI matrix `vanilla` vs
`essentials`.

> **Notification preferences and digests done 2026-11-20.** A member chooses how they hear
> about replies in watched topics: right away (phpBB2's one e-mail per topic until the next
> visit), in a daily digest, or not at all (`core.replyMail`, a preference). The two phpBB2
> choices stay columns on `users`, because the importer maps them, and the account page lists
> them with the new one.
>
> - **Package preferences.** A preference declared with `section: "notifications"` (a boolean
>   or an enum) appears under Notifications on `/account`, labelled `pref-<key>`, so packages
>   add their own without a template.
> - **Digests.** A digest goes out at `core.notify.digestHour` (default 07:00) in the member's
>   own time zone, UTC if unset. The scheduler checks every ten minutes, in `postmodem run` and
>   `postmodem scheduler`; `pnpm dev` has no scheduler. A digest lists each watched topic with
>   its number of new replies and a link to the first one.
> - **What leaves a digest.** A topic goes once the member visits it, or when they can no
>   longer read it. Further replies before the digest don't add it again.

Fixes from trying 0.1.0 (2026-11-19):

- **Header links in Light.** The category titles on the board index are links in the link
  colour, which in Classic Light is the header bar's own colour (`#006699`), so they vanish.
  Links on header bars take the header text colour; the theme tests gain the pairs `link`
  and `headerText` on `headerBg`, and the index gets an axe run in Light.
- **One base style for form controls.** Buttons, selects, text inputs, textareas and
  checkboxes are only styled inside a few areas (`.prefs`, `.form`, `.panel .actions`,
  the toolbar); everywhere else they render as the browser's defaults. A base layer styles
  them all from tokens (primary, secondary and danger buttons, `accent-color` for
  checkboxes), and the per-area rules go. New colour tokens `accent`, `controlBg` and
  `controlBorder`, contrast-tested like the others. Slice 13 builds on this.

> Both fixes done 2026-11-20. Header bar links use `headerText`. axe reports text in its own
> background colour as "incomplete", not as a violation, which is how the bug got past it, so
> the index gets its own contrast check in light and dark. Control borders and `accent` must
> reach 3:1 against the control and the page, and typed text 4.5:1 on `controlBg`. Danger
> buttons are outlined (danger text on `controlBg`): white text on the dark theme's light red
> was about 2:1.

### Slice 13 — Themes (~3–5 d)
The theme (Classic, Modern, Terminal; DESIGN.md §7) and its colour scheme (system, light,
dark) become two choices. Today only Classic exists, `app.html` links it directly, and the

- Themes are chosen per request: the board's default in the admin panel, a member's own

## Risks

| Risk | Mitigation |
|---|---|
| Spam finds the staging board within days | CAPTCHA and new-account limits ship before the board is public (slice 7); registrations can be invite-only during the beta |
| SQLite has one writer; posting adds writes to every page | Short transactions; read tracking and views batched; load test mixes reads and writes |
| Extension APIs designed in M2 turn out wrong | Each lands with a real package; the SDK is only frozen in M4 |
| Real people's data on staging (GDPR/RODO) | Export, deletion and the privacy page are part of M2a, not polish |

## Decisions (2026-11-18)

1. **CAPTCHA:** a self-hosted proof-of-work check (ALTCHA-style), behind a provider
   interface so other providers can be added.
2. **Account deletion:** posts stay under "deleted user"; removing them is a board option.
3. **Staging access:** invite-only during the beta.
4. **Staging content:** the demo board, so no real personal data is on a public machine.
5. **Staging host and domain:** deferred (2026-11-19). The public staging board waits until
   the build is stable and fleshed out, at the end of M3 at the earliest. Development
   continues locally and in CI. The staging guide (CONTAINERS.md §4.6) stays as written.
   Deploying behind an existing reverse proxy, with the real client IP, needs work first
   (#86).
